## Membership and intermediate gates

Every `I3-NN:subcase` row below is one execution record assigned to exactly one
implementing iteration. `npm run reference:verify -- --plan 3 --iteration N`
requires the instances assigned to N and every transitive prerequisite; without
`--iteration` every leaf is required, so the full gate is expected to fail
until iteration 11. Iteration 1 is a review gate and executes nothing. Plan 1's
308 records, Plan 2's records and, once Plan 5 merges, Plan 5's records stay
registered and are required by their own gates; removing any of them still
fails that gate. Iteration 3 delivers the consumer rule and the availability
listing and iteration 5 the explanation and module branches over the same
vocabulary, so the two query iterations are separately gated. If Plan 5 has
not merged when iteration 9 is reached, the I3-12 rows stay `pending`, the
gate reports them as such, and the plan is not complete.

| H | The harness's own copied inventory and assertion stubs. |
| A | Direct owner operations over a copy in the test process: `listAvailability`, `explainAvailability`, `resolveConsumer`, `answerInspection`, `describeOriginals` and `analyzeProject`. |
| B | The batch inspection operation injected by `src/cli-entry.ts`, invoked through `runCli` over a copy with the process working directory set to the named consumer location. |

Evidence kinds: `api` (direct owner operations over A), `unit` (H), `quick`
(in-process runs through real services: Q, or `runCli` over B), `ipc` (real
socket pairs in one process), `process` (P) and `measurement` (instrumented
real processes with retained raw results). A `process`, `ipc` or `measurement`
row is never satisfied by a `quick` or `api` run of the same scenario, and
availability of a capability is never execution of its instances.

Named reference locations, used as consumer locations below and abbreviated in
the table: **CR-reviews** is `subs/workspace/subs/reviews/src` (owner
`workspace/reviews`, ordinary area, profile `[dispatch]`); **CR-shell** is
`subs/workspace/src` (owner `workspace`, profile `[ui, browser, dispatch]`);
**CR-root** is `src` (owner `collection-review`, profile `[dispatch]`);
**CR-contracts** is `subs/workspace/subs/contracts/src` (owner
`workspace/contracts`, no header tags); **CR-core-tests** is
`subs/workspace/subs/reviews/subs/core/src/tests` (owner `workspace/reviews/core`,
tests area, profile `[testing]`). Statement ids (C1, W1, W2, W5, K1, A3, A5,
RC1, RV4, SU1, R1, R2, R3) are the [contract map](../reference-project/contract-map.md#exposing-statements)'s.
The baseline listing for CR-ordinary consumers is fixed by that map: CR-reviews
receives 26 foreign originals — the seventeen `[browser]` vocabulary exports of
`subs/workspace/subs/contracts/src/interfaces/vocabulary.ts` through C1 and W1
(eight schema values, nine types), `InspectionPort`, `createReviewRuntime` and
`ReviewOutcome` from `workspace/reviews/core`, `validateRevisionChain` from
`workspace/reviews/validation`, the four `[dispatch]` protocol types of R1 and
`AppRouter` of R3 — ten of them value-available and sixteen type-only, while
`StatusBadge`, `StatusBadgeProps`, `ReviewPanel` (`ui` missing),
`makeCatalogFixture` and `createTestSystem` (testing origin) are blocked and
therefore absent from the listing.
