## What a released consumer can use

`ramify.ts/cli` exposes `OwnershipDocument` and `ownershipDocumentSchema` through the public package entry. Its schema implements `parse` and `safeParse`. `ramify ownership --root <project> --path <path> --format json` performs fresh inventory acquisition and returns `ramify.ownership/1`. An answered document has `status: 'answered'`, `exitCode: 0`, canonical `root`, acquisition `inputId`, ownership scope, paths and warnings. Acquisition failures have `status: 'invalid'` with exit 1, or `incomplete`/`unavailable` with exit 2; they contain diagnostics and available stages, a canonical root only when established, and no success-only scope/input/path fields. Cancellation exits 130 without an ownership document. Repeated `--path` values retain first-request order, and a missing path defaults to `.`. The command does not connect to the daemon or run catalog, linking or import decisions.

`ramify check --changed <path> --format json` now emits `ramify.check/4`, and generic unavailable commands emit `ramify.cli/2`. Invalid or incomplete resident analysis retains current producer findings, available stage execution and optional `ramify.recovery/1` history. `RecoveryEvidence.lastCompleted` identifies the last **completed** resident analysis, even if its check found ordinary import violations. `changes.paths` are observations since that baseline, not a causal diagnosis or proposed rollback. A null baseline with unavailable coverage means no completed baseline was established. Watcher loss, overflow, byte pressure and eviction can name known gaps; a new context after restart cannot reuse the prior context's identity, and the current history producer does not emit a `context-restarted` gap. Current invalid analysis cannot answer affected selection or publish new generated views. Fresh batch Analysis/3 and Ownership/1 do not contain recovery. A completed checked revision omits recovery; a not-checked outcome can retain prior context evidence when cleanup failed after earlier execution.

The daemon protocol is `ramify.ipc/3`. New peers strictly validate typed diagnostics, stages and recovery in both service value and error carriers. `/2` and `/3` handshakes reject one another before operations; there is no downgrade or field-stripping compatibility path. Built socket evidence proves both wire directions. Installed-process evidence shows a new client injected with an old discovery record reports explicit `incompatible`. The old `/2` client's discovery parser reports a generic unavailable/malformed-record refusal for a future `/3` record; a controlled private metadata/socket relay demonstrates its actual handshake with a new daemon returns explicit incompatibility before a request. Normal discovery separates builds by build key, so the injected record and relay are test controls, not an unmodified discovery scenario. Consumers should restart old clients/daemons together when adopting a released `/3` build.

The complete field and status contract is in [contracts.md](contracts.md), with executable strict schemas in the CLI and daemon owner tests. Avoid reducing diagnostics to the first message: IDs, codes, primary and related spans when the producer supplies them, and stage references are part of the evidence. Spanless acquisition failures retain their file path in the message and do not invent a location. A service error keeps its scalar `details` map for the old purpose and exposes typed `diagnostics`, `stages` and `recovery` beside it.
