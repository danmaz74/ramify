# Iteration 4: Presentation, trials and completion

**Goal:** make the measurement understandable to a person, validate it through
the complete loop and close the plan with retained evidence.

## Prerequisites

Iterations 1–3 complete.

## Work

1. Add a Token efficiency panel to the Run page. Show `T`, `A`, `D`, `C`,
   `S0`, `g(S0)`, `U`, `K`, their states, policy version and endpoint
   identities. Put production/test, provider/model, coverage and diff-recipe
   detail behind progressive disclosure.
2. Render values received from the harness. Client code may round for display
   but contains no metric formula.
3. Give the older KPI table the presentation labels in the main plan while
   keeping raw compatibility IDs visible. Add its declared-scope and
   invocation-numstat qualification.
4. Add the Context limits panel from `context-limits/1`: automatic total, exact
   overflows, budget returns and compactions, with role/invocation detail,
   coverage and the following workflow action. Do not calculate counts in the
   browser.
5. Sweep current metrics, architecture, README, Plan 3 completion and source
   prose for the agreed terminology. Do not rewrite compatibility identifiers
   or historical iteration evidence merely for style.
6. Run an integrated fixture delivery with known source edits and deterministic
   provider-accounted usage. Retain the run directory and independently
   reproduce all eight displayed inputs/results from its records.
7. Run companion cases for zero source change, incomplete usage, unavailable
   final inventory and an old Plan 3 run.
8. Add a context-limit fixture containing a budget return, threshold
   compaction, overflow-triggered compaction, explicit compaction and an
   interrupted attempt. Independently reproduce the displayed summary and
   ordered occurrence list.
9. When pi credentials are available, run a small real delivery and retain its
   provider/model accounting and token-efficiency response. If credentials are
   unavailable, record that TE19 remains outstanding; never substitute scripted
   usage as live provider evidence.
10. Run `ramify measure`, record exact/subtree measurements after the plan, and
   assess whether KPI/evidence responsibilities now justify a child module. Do
   not extract one here.
11. Write `completion-report.md` with every completion-gate item, acceptance
   evidence, commands, live status, limitations and any follow-up boundary
   brief.

## Acceptance cases owned

TE16–TE19, TE23 and the presentation half of TE04.

## Exit evidence

- Browser tests for measured, not-applicable, unavailable and incomplete-run
  presentations.
- Browser tests for every context-limit mechanism, an in-progress compaction,
  partial historical coverage and no occurrences.
- Retained integrated fixture evidence and independent recomputation.
- Real pi evidence or the explicit outstanding credential limitation.
- Before/after module measurements and the boundary assessment.
- The completion report and the four passing standard project checks.
