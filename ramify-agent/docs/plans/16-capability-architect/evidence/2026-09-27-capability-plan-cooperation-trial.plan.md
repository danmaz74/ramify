## Original need and provenance

CLI engineer submission: `turns/01-a-engineer/submission.json` (reviewed revision 0).
A CLI reader of a denied import needs the same actionable block in full and changed/hook human forms. For the initial no-exposure case, it must identify importing file, backticked symbol, declaring file and declared owner; say the owner does not expose it to the importer so the import is denied, including for type-only imports; list exposures as none; show no proposal; and omit internal `owner:file#binding` keys. The CLI must relay real Analysis evidence. JSON has `details`, `proposal: null`, and role-labelled related locations; exit 1 and allow/deny behavior stay unchanged.

The CLI engineer identified `subs/cli/src/format.ts` (full and changed human renderers), `changed-command.ts` (report-to-delta mapping), `command-support.ts` (full report output), and `subs/cli/src/interfaces/cli.ts` (changed document). Existing real batch/resident tests are at `src/tests/batch-cli.test.ts` and `src/tests/resident-cli.test.ts`. It proposed a concrete fixture from `src/tests/fixture.ts` with `privateValue` in root `src/interfaces/api.ts` imported by `subs/consumer/src/use.ts`, while root exposes only `value`. Expected output is independent of any proposed provider algorithm.

The full original plan also requires five denial codes, role-labelled related locations, one-edit-only proposal behavior, not-checked explanations, size limits, deterministic output, empty fields on unrelated diagnostics, and reference-harness rendering. These remain requirements for the feature, outside this first scenario's implementation target. The later one-edit proposal case tests whether the initial capability/interface still fits.
