# Acceptance cases and witnesses

These are required cases for [Plan 21](main-plan.md). A result receipt names the
case, fixture, command, source/provider identity and observed outcome. Existing
passing tests are reused where they prove the case; new assertions target the
changed behavior. Do not count a scripted provider answer as real conformance.
The [provider contract review](provider-contract-review.md) details prerequisite
witnesses for PB3-A02, PB3-P01 and PB3-T06; its current API smoke does not
mark any acceptance row passing.

## Workflow scenarios

### Auxiliary-source repair within an owner

Given F1 and an ordinary assignment for `app/a` with no included child,
when the engineer repairs `subs/a/scripts/task.ts`, the write is permitted,
the real hook analyzes it and configured checks report test health. The
architect assesses the repair and reports its judgment.
A write to `subs/a/subs/deep/src/task.ts` is blocked until a new assignment
explicitly includes that child subtree. Both decisions retain the scope revision.

### Included independent project

Given an owned-nested-project nested project with explicit inclusion and instructions,
when its files change, the hook says not-analyzed and audit follows its
configured project policy. The architect inspects the independent project's work. At final acceptance, the provider runs that project's own
audit from its root. Its failure keeps the whole plan unaccepted even if the
enclosing audit passed; its report remains separately retrievable.

### Documentation and applicable evidence

Given a project whose producer policy explicitly ignores a documentation tree,
when only that tree changes, a full request can reuse applicable full evidence
under A+. The UI shows reuse and the original audited commit. Given an agent
documentation change that merely selects no module under Ramify, the harness
does not infer the same full-reuse permission; it follows the provider result.

### Interrupted capability work

Given an ordinary engineer suspended for capability work with open scratch,
when a provider engineer completes an audited change and the service stops
after publication, resumption retrieves the published result, preserves both
captured scopes and the consumer's scratch, and continues without a second
writer or an unnecessary verification replay.

### Incomplete proposal returns to the engineer

Given an assignment naming two scenarios to bind, when the engineer proposes
completion declaring one, the harness rejects the proposal naming the other
and the same turn continues; nothing is committed or audited. When the
engineer then declares both, the gate commits the candidate and requests the
audit; when it instead reports partial work, the report is accepted and the
local architect decides what follows.

### Bound with fakes, then done

Given a registered scenario assigned to a consumer engineer while its provider
is delegated, when the engineer proposes completion binding it against
`SendEmailFake`, the scenario becomes `bound` with that fake recorded, the
pending tag comes off, and the audit runs it green. The architect sees
"bound, fakes: SendEmailFake" and does not report it done. After the provider
lands and the consumer is rewired, the next proposal binds it with no fakes,
and the architect reports it done.

### Forgotten report and independent audit health

Given a registered acceptance scenario and completed engineer work,
when a full audit passes but the architect requests completion without a done
report, the request is rejected naming the ID and the turn continues. A
trusted report in that turn resolves it, with or without `where`. If work was
forgotten, the architect continues ordinary bounded coordination instead.

Given a recorded done declaration and a later audit failure, the declaration
stays recorded and complete diagnostics remain available. The architect may
investigate and revise its judgment. Final verification cannot pass while its
required full audit remains failed; that execution result does not reinterpret
the architect's declaration.
