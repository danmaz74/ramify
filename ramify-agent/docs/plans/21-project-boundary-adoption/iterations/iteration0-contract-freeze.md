## One obligation projection

The run ledger supplies one projection keyed by stable obligation ID. Accepted initial-analysis scenarios retain their existing `sc-NNN` records and are registered `pending` when the analysis is accepted. An entry scenario's responsible architect is the local architect of its entry work item; an integration scenario belongs to its integration work item's local architect. A delegated capability task contributes one default outcome obligation under its existing `cap-NNN` ID, owned by that task's coordinating architect. This does not transfer the consumer's entry or plan scenarios to the provider. The original request, examples and approved requirements remain immutable context.

The responsible architect may explicitly register a capability-plan use case as a separate scenario obligation or a required test under its current work item or capability task. A case registration has `{ kind: 'scenario', case: existing case ID }`, is accepted only from that capability task's current architect, and projects the stable ID `<task>.case.<case>`, for example `cap-001.case.need-001.ex01`. It must reference a use case in the current accepted plan revision. Merely preserving an original example or adding a use case to the plan never registers it. A future case enters the existing plan-revision authoring path before it can be registered. Registration does not create a feature file, check or test obligation automatically, and cannot transfer authority over a consumer's `sc-NNN` scenario. A test registration has `{ kind: 'test', description: nonempty text }`; the harness allocates `test-001`, `test-002`, and so on from the count of accepted test registrations in this run, never from an agent field. Registration stores the parent work-item/task authority, declaring invocation and case reference or test description as an `obligation-registered` event in the existing run ledger. The event payload is `{ id, kind: 'scenario' | 'test', responsible: { kind: 'work-item' | 'capability-task', id }, by, submission, case?, description? }`; `case` is required only for a scenario, `description` only for a test. It enters `pending`. Ordinary tests do not register themselves. Reject a conflicting repeat; replay of the same accepted registration is idempotent. Registration adds reporting granularity and cannot remove an existing scenario, example or requirement. The one read projection folds existing scenario/capability records and these accepted events; there is no second persisted registry or status store.

The initial architect submits the scenario forms through `submit_initial_analysis` (`analysis/submission.ts`); the harness allocates their IDs through `scenarios/records.ts`. Those `sc-NNN` scenarios are already required under stable entry/work-item ownership and need no extra registration. An integration scenario is registered at that point with a stable responsible key `{ kind: 'integration-scenario', id: 'sc-NNN' }` and the recorded common-ancestor owner. Its future work item has `origin.integration` equal to that ID; only that work item's local architect can report it done. Before creation the ID remains owned by this stable key, but no invocation is licensed to report for it. Local architect authority is the active work-item invocation checked by `work/submission.ts` and `run/service.ts`. Capability architect authority is the active task, current plan revision and coordinator invocation checked by `capability/submission.ts` and `capability/state.ts`. A module path alone never authorizes a report. Engineer submissions cannot declare `done`.

## Submission fields and timing

Extend the existing local architect and capability action submissions with optional `registrations` and `reports` arrays, including on an `assign` action. `registrations` contains the two shapes above. `reports` contains `{ id, judgment: 'done' | 'bound', basedOnRevision: nonnegative integer, where?: short nonempty text }`. `bound` is accepted only as an explicit architect revision of a prior `done`; a new `done` report may move an obligation directly from `pending`, since the architect's judgment needs no binding, file or audit prerequisite. These arrays permit reporting while coordination continues; a completion or handback request may carry reports in the same accepted submission. The arrays default to empty, and existing coordination actions suffice without a report-only action, clarification turn or new budget. Validation sees the current ledger and validates all IDs, actor authority and revisions before any action effect, gate or candidate commit.

An architect report names an obligation ID and a judgment `done` or an explicit revision from `done` to `bound`; `done` means correctly implemented and passing in the architect's judgment. It may carry one short optional `where` string. The harness stores that text and invocation/source provenance but does not resolve it, read the cited file or compare it with tests. Each obligation's report revision starts at `0` on registration and increments only on accepted architect reports. Engineer bindings and fake-list updates do not increment it or invalidate a judgment. The report's `basedOnRevision` guards against a stale competing judgment; `obligation-reported` carries `{ id, judgment, basedOnRevision, revision: basedOnRevision + 1, where?, by, submission }`. The accepted-submission/effect identity is checked first: replay of that same accepted submission applies no effect and raises no stale-revision error. A distinct deliberate report with the same state or a changed hint must name the current revision and records a new revision; a competing old revision is rejected. Existing accepted-submission journaling and idempotent effects/replay persist registrations/reports. No new transaction mechanism is introduced. A later source change or audit outcome does not edit an architect report.

In the new policy, replace the existing local `assignment.scenarios` list with `assignment.obligations: string[]` and use the same list on capability assignments. The responsible architect chooses the exact registered IDs delegated to this engineer: an initial `sc-NNN`, the task's `cap-NNN` outcome, a registered `<task>.case.<case>`, or a registered `test-NNN`. The default capability outcome is not bound automatically; an engineer binds it only when the architect explicitly includes it in an assignment. Replace `completion-proposed.scenarios` with `completion-proposed.bindings: { id, fakes? }[]`; this is the same assignment-to-submission binding path generalized to the one obligation projection, not a parallel binding registry. `fakes` defaults to `[]` and is a de-duplicated list of fake class/export names carrying the existing `Fake` designation. `obligation-bound` carries `{ id, fakes, by, submission }` in the existing run log. The harness validates that each ID is in the captured assignment list, registered for the assignment's responsible work item/task, and appears once, then records the submitted list and invocation. It does not inspect source to confirm the declared binding or fakes. A repeated binding replaces the recorded list. If the obligation is already `done`, the list changes but its status stays `done`; only the responsible architect can explicitly revise it to `bound`. A `partial` submission may describe unfinished work without declaring every assigned obligation.

The three statuses are `pending` on registration, `bound` on an accepted engineer binding, and `done` on an accepted responsible architect report. A trusted architect report may move `pending` directly to `done`. The accepted submission alone moves them. Remove the old `scenario-due`, `scenario-implemented` and withdrawal transitions, pass-driven promotion and repair-exit reset. The feature renderer removes `@ramify-pending` whenever a ScenarioRecord's status is `bound` or `done`, including direct `pending` to `done`; both remain eligible for the project's configured Cucumber checks. Test and capability-case obligations have no feature rendering merely by being registered. Associate raw Cucumber results with identity tags for display and diagnosis, never to move status. An integration work item becomes due when all its sub-scenarios are `done`, exactly once through the existing work-item creation effect. There is no separate integration-readiness judgment.

## Structural rejection and continuation

For a `completion-proposed`, every ID in the assignment's `obligations` list must occur exactly once in its `bindings`. This includes every named scenario and any explicitly assigned case/test obligation. Missing IDs are reported by `validateEngineer` as submission errors before a candidate commit, audit or review. A binding for another actor's ID is rejected, even if its string exists elsewhere in the run. `partial` is exempt. The list is structural: the harness makes no correctness claim about the binding.

For a local `request-completion`, compute required IDs owned by that work item from the ledger after applying reports in the same proposed submission. For capability `request-handback`, do the same for the task's default outcome and separately registered obligations. If any remain without `done`, reject the entire submission naming each ID. Keep existing non-test structural blockers such as an active child or unfinished assignment; remove per-example evidence/test matching and source-file pass coverage. Rejection uses `SubmissionJudge` and `rejectedSubmissionsPerTurn`, so the same invocation receives path-specific errors and may assign further work, report done, report a blocker or submit partial. Exhaustion is `invalid-submission` with the outstanding IDs, not a verdict about code. No rejected action writes records. Accepted reports survive interruption in the ledger; the existing effect and writer recovery prevent duplicate work.

The architect briefing offers the current obligation projection, earlier reports, current source revision and changes since its last decision, complete audit diagnostics, reviews and the ordinary Git/source inspection tools. The architect decides whether a prior judgment needs revision. No change-path mapping or failed audit retracts a declaration.
