# Plan execution decomposition map

Status: design proposal, 2026-09-24, against `ramify-agent` at `7d6af7f`.

This proposal starts from the [dashboard element and relationship catalog](2026-09-24-dashboard-elements-and-relationships.md). It specifies an interactive view of one plan **run**: where implementation began, how it was decomposed, which iterations and sessions did the work, what each gate concluded, and what is happening now. The broader [dashboard proposal](2026-09-23-plan-execution-dashboard/design-proposal.md) covers other run views; this document concentrates on the execution map, its companion modules map and its transcript workspace.

## 1. The organizing model

The map has one root for each top-level capability assigned from the plan. A capability expands into its work item or work items. Each work item contains an ordered sequence of **assigned iterations**, with a persistent local architect session lane above them. A new provider need can branch from the planning decision or iteration that caused it. The provider has its own capability, work item, local architect lane, and iteration sequence. The consumer's later verification is linked back to the provider's conformance.

```text
Top-level capability A                                           [working]
   scenarios: sc-001 "renders the status" ✓ · sc-002 "uses tone" pending
└─ wi-001 · module project/ui                                     [yielded]
   local architect ses-002:  inv-002 outline ─ inv-008 assess ─ inv-017 resume
   implementation:            i01 ── i02 ───────── i03 ── wait ── i04 verify
                              │      │                         ▲
   engineer sessions:         ses-003 ses-006                   ses-018
   gate attempts:             ga-002✓ ga-005✗ → repair → ga-006✓ ga-019✓
                                     │                         │
                                     └─ need B → placement → ct-002 [working, blue]
                                                      │         │
                                                      ▼         │
                                Capability B / wi-007            │
                                module project/service           │
                                local architect ses-011         │
                                j01 ── j02 ── provider conformed ┘
```

This sketch is hypothetical: the [recorded real pi run](2026-09-24-dashboard-elements-and-relationships.md#1-the-elements-at-a-glance) has one work item and no contract engineer or provider branch. It illustrates a required layout case, not observed run evidence.

The underlying model is a graph. Capability dependencies are many-to-many, and work items can follow up earlier work. The tree is a **reading layout** rooted at entries, not a claim of unique parentage. The map gives each capability and work item one canonical implementation card. Other consumers show a reference tile pointing to that card, with a reverse list of consumers. A dependency cycle appears as a cycle group with its notice; expansion stops at a reference rather than recursing forever.

### Structural and temporal relationships

| Relationship | Visual form | Meaning |
| --- | --- | --- |
| Entry capability → work item | Containment | Work scheduled for that entry. |
| Entry capability → scenarios | Named rows inside the capability card | The tracked acceptance scenarios assigned to that entry, each with its latest execution result and lifecycle state. |
| Work item → assigned iterations | Horizontal numbered sequence | Actual assignments in their recorded order. Outline stages and later forecasts are shown in the work item's planning drawer, not as finished or scheduled iteration cards. |
| Capability → dependency | Link between capability cards | The capability registry says the consumer needs this capability; tentative links are labeled forecasts. |
| Request or iteration → provider | Branch through placement, requirement and contract | The recorded cause of new provider work. A placement decision alone does not imply implementation. |
| Provider conformance → consumer verification | Return link | The consumer's requirement is verified after real provider work. A fake-backed consumer gate alone leaves this link open. |
| Consumer → cross-module requirement | Colored branch with a named contract and provider module | Gray before work on the agreement begins, blue once contract or provider work starts, green when that consumer's current requirement is verified. The provider's own stage is labeled separately. |
| Work item → follow-up item | Continuation link | More work for the capability after a prior item, with both histories retained. |
| Session → work/request/iteration | Session lane or marker | Where the harness says that conversation reaches. |
| Gate → subject | Result marker | One attempt at its checkpoint, including failed attempts that preceded a pass. |

### Full module paths on work

Show the **full declared-name module path from the project root**, such as `collection-review/workspace/shared-ui`, on the work item header beside its ID and goal. The last segment alone is insufficient. The header is the shared context for the local architect lane, its iteration sequence and its gates. It remains visible while inspecting that work item, so those rows do not repeat the path. A compact capability root shows its current owner or proposed module path before any work item is expanded. When its owner and the work item's module differ, show both full paths with their distinct labels; otherwise one visible path is enough. The filesystem directory belongs in module detail.

An iteration inherits the work item's module path in the compact sequence. Show additional full paths when its recorded write scope includes other modules or child subtrees, and make the complete scope available on selection. A provider branch labels the provider work item's full module path. Session windows show the associated work-item path in their header so the context survives when windows are moved away from the map. Paths may wrap at `/` on narrow cards or windows; they are not shortened to the leaf name or hidden behind a tooltip. An initial architect session has run-wide scope; a global fork shows its request and candidate or decided owner path rather than implying it was assigned implementation work in one module.

The initial architect session belongs at the run header. Global forks attach to placement requests and link back to their source point in the global architect context. Integration work items and gates that concern several entry capabilities appear in a run-wide band with links to the affected roots. Readiness and final gates also live in that band. Standalone sessions remain in the project-wide session view because they have no plan run.

## 2. Screen layout

```text
┌ Plan › Run 2026…  working · version 123 · now: wi-001.i03 · coverage ┐
│ Roots / focus path       Execution canvas      Modules map   Sessions │
│ A  working  2/3 sc      [wi-001 · project/ui]   project/ui ●   3 open │
│ C  completed 1/1 sc      ╲ branch to provider B  project/svc           │
│                                                                      │
│ Time rail: phases | sessions | iterations | gate attempts | now       │
└──────────────────────────────────────────────────────────────────────┘
    ┌ ses-002 · local architect · suspended ┐  ┌ ses-006 · engineer · live ┐
    │ draggable, resizable transcript       │  │ transcript · Jump to live│
    └─────────────────────────────────────────┘  └──────────────────────────┘
```

The run header shows state, phase, current work and run version. Its **Now** control focuses the current recorded work or running gate; if several targets are current, it opens their short list. Only a session currently awaited by the harness or a gate with a recorded start and no ending pulses. No pulsing mark is inferred from a merely open work item, a suspended session or an old run without a start event. Motion stops on completion and respects reduced-motion settings. The roots list is a compact navigator with entry state and scenario fraction. Each entry card in the execution canvas lists its associated scenarios by name. The execution canvas shows the selected root and its expanded descendants. A smaller modules map shows the current module hierarchy beside it. The time rail has real event order and highlights the selected element's history. A session shelf lists every run session, including finished, suspended, interrupted and replaced ones, with role, state, reach and last change. It includes pi sessions and labels scripted sessions by executor. Filters narrow that list without changing completeness; a bounded response states its `shown / total` coverage. Session windows float within the dashboard and remain open while the user pans either map or selects another root.

The canvas should initially show entry cards, their current work items, and the branch containing current work or the latest issue. Expanding a work item reveals its sequence; expanding a provider reference moves focus to the canonical provider card. A focused path preserves its map positions as new records arrive; a deliberate relayout action can tidy the view. Dense subtrees collapse to a count and status summary. Every count states `shown / total` when the answer is bounded, and missing dependency targets get explicit reference tiles.

Selecting any map element opens a compact facts panel with its state, reason, related elements, source records and event moments. Selection and the focused root have stable links. The time rail can select an event and highlight its causal path; selected-element moments have distinct ticks. The rail is ordered by recorded event sequence, not proportional elapsed time, so an idle period cannot stretch it. Show actual timestamps and elapsed gaps in event detail; a time-proportional mode with folded gaps is a later design choice. It shows recorded milestones against the **current** tree; historical tree playback needs published revision snapshots and is a later contract.

Use one semantic palette across the maps and detail: gray `todo`, blue `working`, green `completed` or latest valid pass, amber attention, red failure, and violet **worked in** participation. `Unavailable` gets a distinct patterned neutral treatment and text, never the plain `todo` mark. Session roles have a separate accent and icon vocabulary, applied consistently on markers, the shelf, time-rail lanes and window headers: initial architect `compass`, global fork `branch`, local architect `blueprint`, engineer `tool`, contract engineer `link`. Candidate role accents are cyan, magenta, teal, indigo and umber respectively; none uses the participation violet token. Because five role hues cannot all be widely separated from six semantic hues, every role mark also carries its icon and a readable role label. Fix the light/dark token values and contrast in the first UI contract review; use color only as a secondary cue for status, role and coverage.

A header issue count by severity needs the shared dashboard's complete, revision-bound issues projection. This execution map already marks failed gates, unavailable data and other evidence at their subjects, but those marks are not a census of all recorded issue kinds. Add a count-and-cycle control when the shared projection is available; until then the header makes no `any issues?` claim from a partial count.

### Companion modules map

Place a compact, independently **pannable and zoomable** modules tree beside the execution canvas; the execution canvas is also pannable and zoomable. Each has its own fit-to-view and zoom controls. Moving or zooming one map does not move the other. The smaller tree uses the current module hierarchy, with proposed but undeclared modules drawn as dashed shells and unplaced modules listed outside the tree. A module node identifies the full declared-name path; at an overview zoom where text is unreadable, clicking the node shows that full path in its detail panel. A narrow layout can put the same zoomable map in a drawer rather than compressing both canvases until their labels are unreadable.

Use a **violet stripe or dot labeled `worked in`** for a module with recorded implementation activity in this run, such as a started work item or a session attached to that module. Neutral slate means no such activity is recorded. Initial association, a proposed placement, a contract request and an authorized iteration write scope alone do not count as work performed. Keep capability completion green, work in progress blue, warnings amber and failures red; the violet module mark describes participation, not completion. A strong outline identifies the currently selected or highlighted module independently of its participation mark. A parent module can carry a count of involved descendants without being marked as directly involved.

Clicking an execution-map element highlights its directly associated module or modules in the modules map. The work item and local architect lane use the work item's module; a contract branch can identify both consumer and provider with role labels. A run-wide session or gate with no defensible module association leaves the modules map unselected. Clicking a module highlights directly associated execution nodes across capability roots and shows their count and a jump list, including matches inside collapsed branches. Each collapsed execution branch also carries a badge such as `3 inside` for its hidden direct matches; shared canonical nodes count once per branch. A parent module carries an involved-descendant count without gaining the direct **worked in** mark. Selection is persistent until changed or cleared; keyboard activation has the same effect. There is **no hover-driven cross-map highlighting**. A single selection state and a typed element-to-module index drive both directions, so shared providers and multi-module scope do not create duplicate implementation cards. An iteration's authorized scope is labeled separately from modules where work was actually recorded.

The existing packaged module-tree canvas supplies hierarchy layout, selection, collapse and zoom controls, but the current By module node bodies are too large for this companion. Use compact bodies and preserve module paths in the selected detail. If that canvas cannot keep the smaller map readable, use a simpler hierarchy renderer that still supports **both panning and zooming**, along with click selection and bidirectional highlighting. The module comparison's current-tree revision, run version, coverage and unplaced cases must remain visible: a missing or partial answer is not a slate `no work` result.

**Module change volume.** Show `+LOC / −LOC` beside each module from the run's retained `ramify-agent.line-events/1` records. Each settled writer invocation records added and deleted lines per path with its exact module owner. Sum the module's own text-path counts across those invocations, including failed or repaired attempts, and label the figure **captured writer changes**. The public `/metrics` answer exposes only invocation-level totals, so the harness must publish this grouping and its invocation provenance; the web must not infer changed files from iteration scopes. The figure updates when a writer settles, not continuously while it works. A parent node does not silently include child-module files.

This is a useful activity measure, not a precise net change or exhaustive edit history. Each invocation compares two worktree diffstat snapshots against the same accepted commit; a further edit can be missed when the diffstat counts do not grow, and an edit later reverted can be invisible. Explain that limit in the module detail even when capture reports `complete`. Show coverage for settled writers: if a line-event record is missing or partial, label the known subtotal **partial** and include its gaps. Show a running writer separately as pending. Keep paths without an owner in `unmapped`, count binary changes separately, and never turn unavailable data into `+0 / −0`. Beside each numeric `+LOC / −LOC`, draw a compact diverging bar with additions and deletions on opposite sides of zero. Both sides use one scale: the greatest known absolute side among modules in this run. Use neutral activity fill so change volume does not imply success or failure. Hatch a partial subtotal and keep its `partial` text; do not draw a zero-length bar for unavailable data. If every known side is zero, show the numbers without a bar.

A future refinement may add a separate **net accepted change** measure from the run's source-base commit to its latest accepted commit. The existing Git boundary can return per-path `diffNumstat(from, to)`, but that measure needs its own module attribution and coverage rules. Do not replace the captured-writer figure with that different meaning without relabeling it.

### Capability and scenario detail

Color every registered capability card, top-level or lower-level, from its published `CapabilityProgress.state`: **green for `completed`**, blue for `working`, and neutral for `todo`. The roots navigator uses the same colors. A forecast retains a distinct dashed treatment and is never green merely because a related capability completed. The card also carries the state label, so color is not the only signal. Its detail panel shows the harness's reason and evidence gates. Capability green means **currently verified in this run**; scenario green has the narrower meaning below. Even if every entry scenario row is green, the capability remains blue while provider requirements or other verification remain open. Two labeled compact summaries on an expanded capability card show (1) its scenarios by latest real result and (2) direct consumer requirements verified out of the known total at their current revisions. The latter excludes provider obligations merely referenced by this capability and deduplicates shared requirements. A zero requirement total says `no cross-module requirements`; partial membership says `known / total unavailable`, never `0/0`. The published capability reason remains visible because other gates or work can also keep it blue. If evidence is reopened and the published state returns to `working`, its green treatment clears on the next run-version update.

Every top-level capability card has a named row for each tracked scenario whose `entry` is that capability. The focused card shows its complete scenario list. A collapsed root shows one dot per associated scenario, ordered by scenario ID and colored by the same latest-real-result rule as its row, through 20 scenarios. Above 20, it uses a stacked result bar. Both modes retain a textual count by result and expand directly to the names; the tiny dots are overview marks, not the only click targets. A long list may use an internal list viewport, but each scenario remains selectable by name and the card states how many rows are shown. An integration scenario belongs in the run-wide band, linked to the entry scenarios it combines; it is not assigned to one entry by appearance alone.

The scenario row shows its name and **latest recorded non-dry-run result**: green for `passed` while the scenario remains `implemented`, red for `failed`, and distinct labeled treatments for `undefined`, `pending`, `ambiguous` and `skipped`. Before any such result, it shows the lifecycle state (`pending`, `bound` or `declared`) without green. A withdrawn scenario also loses green even if an earlier gate passed; its historical pass remains in detail. The row names the gate and mode (`quick` or `full`) that produced its displayed result. A later failure replaces an earlier green result, while the history retains both. A dry-run pass is labeled as a dry run and does not turn the row green. The `implemented` lifecycle badge remains separate: it records that a gate first implemented the scenario, while the result color reports the most recent execution of that scenario. Every color has a text or icon label. A green row therefore means **last real execution passed and the scenario is still implemented**, not that a newer commit or the whole capability is verified.

Clicking a scenario **name** opens a detail panel with its entire frozen Gherkin `Scenario` block, preserving the title and every Given/When/Then line. The panel shows its origin in the plan or architect analysis, full owner module path, current lifecycle state, the gate that first implemented it, and all gate results in order with links to their attempts. Clicking the enclosing capability card opens the **full capability description** as recorded by the initial architect, without truncation, beside its owner, state and source. Scenario-name clicks select the scenario rather than also selecting the capability. Both panels have stable links and return to the same map focus when closed.

For a lower-level registered capability, the corresponding full text is its recorded behavior, labeled as behavior rather than an entry description. That text currently needs publication from the registry; until it is available, the panel explicitly says that the full behavior is unavailable and links to the registering decision. A forecast shows its hypothesis and rationale as a forecast, not as a confirmed capability description.

## 3. Work item detail: local architect, iterations and gates

A work item card shows its associated full module path in its header and has three aligned lanes:

1. **Local architect.** One session lane spans the work item. Its invocation markers attach to outline revisions, iteration assignments, result assessments, placement requests, yields, resumes and completion requests. The lane persists between invocations while the session is suspended. Clicking the lane opens the transcript; clicking a marker opens that invocation's chapter. If a session is replaced, both sessions remain visible with their lineage link.
2. **Implementation.** Each assigned iteration is a numbered card with kind, stage, goal, any scope that differs from the work item, result (`accepted`, `partial`, `unsuitable`, `exhausted`, `superseded`, or still open) and its engineer or contract engineer sessions. The outline drawer shows successive plan revisions and stages separately, so a forecast does not masquerade as an assigned iteration.
3. **Verification.** Every gate attempt is a separate marker attached to its iteration or work item. Its center contains a verdict glyph (`✓` passed, `✗` failed, `?` not verified; a distinct running mark) and its outer ring reports the **independent audit result**: solid green for passed, solid red for failed, broken amber for incomplete, and no ring when audit is not applicable, including readiness. A gate whose audit has not started or whose result is unavailable carries an explicit label rather than borrowing `no ring`. The marker names the checkpoint and repair round in text and accessible name. Failed and unverified attempts remain beside the repair invocation and later attempts. Typed `repair-of` links draw a short inline chain such as `✗ → ✓ · round 2`, with each attempt still individually selectable; a long chain collapses after its first and latest attempt with a count. A committing gate shows the commit and its audit result; readiness has no audit.

Selecting a gate opens its cause, next action, ordered checks, scenario summary, guarded changes, commit and audit evidence where recorded. The first map layer needs the **gate and audit verdicts**. Individual test cases and step bindings remain deeper drill-ins. A failed gate followed by a pass is shown as two attempts, not one green aggregate. An iteration's result and a work item's completion are displayed from their own records; they are not inferred from the last gate color.

When an engineer requests a cross-module contract, a contract engineer session appears at that requesting point. A branch shows the resulting contract, requirement and provider obligation. If the provider work item starts later, the branch remains visible as pending until it exists. The consumer can continue local work against a fake, then yield, then receive a verification iteration. The link closes only on requirement verification. A request resolved through reuse or exposure without provider implementation links to the existing capability without creating a new work branch.

### Cross-module requirement colors

Put a labeled status chip on each **consumer's cross-module need branch**. Before registration it names the contract request; after registration it names the contract ID, current revision, requirement ID and full provider module path. The color describes that consumer's current need. A shared provider may therefore have one green consumer link and another blue one. The contract record says what was agreed; its registration alone does not mark a fake-backed requirement done.

| Color and label | Fake-backed cross-module need at its current revision |
| --- | --- |
| Neutral gray · `todo` | The cross-module need has been requested, but neither contract engineer nor provider work has started for its current revision. |
| Blue · `working` | Contract engineering or provider implementation has started and the consumer requirement is still open. Sub-labels distinguish `establishing contract`, `provider not started`, `provider working`, `provider yielded`, `provider conformed`, and `consumer verification`. A registered fake-backed agreement and a fake-backed gate pass remain blue. |
| Green · `completed` | The harness has recorded `requirement-verified` for this requirement revision after provider conformance and consumer verification. |

The contract engineer's session and the contract gate show agreement work independently of provider implementation. A blue branch can therefore carry the sub-label `provider not started`: the agreement work has started, while provider implementation has not. An `access-only` contract has no obligation, provider work item or fake-backed requirement. Its agreement chip is gray while requested, blue while contract work has started, and green when the passing contract gate registers access. Label it `access established` so it is not mistaken for provider implementation or completion of the surrounding capability. If the evidence is reopened at a new revision, discard the old green for the current chip and derive its color from the new revision's work and verification. A failed gate keeps its red gate marker and issue; it does not invent a `failed` requirement state. If the provider binding or current revision cannot be read, show `unavailable` instead of gray.

## 4. Transcript workspace

Clicking any session marker or shelf row opens one in-app window for that session. Clicking it again raises the existing window. Each window can be moved, resized, minimized, maximized and closed independently. The header carries a restrained tint and icon from the shared role palette and shows the role label, session ID, state, the work item, iteration or request it reaches, and its associated full module path where one exists. The window offers **Focus on map**, **Open full page** and a link to its current invocation. Focus on map reveals a collapsed ancestor if needed, focuses the session marker or run-band mark, and briefly outlines it so the window can be matched back to the map; with reduced motion the outline appears without flashing. If no marker is available, focus moves to the session shelf row. Closing a window changes only the browser workspace.

Each window retains its own transcript cursor, scroll position and follow mode. A live window opens at the latest complete entry and follows new entries while the reader remains near the bottom. Scrolling back pauses automatic scrolling and shows a new-entry count with **Jump to live**. A suspended session continues to follow because the harness may resume it. A finished or interrupted session shows its recorded end and stops polling after trailing entries arrive. Missing or unreadable transcript lines, delayed first entries, and a lost connection are stated inside the affected window; the last successfully read content stays visible.

Invocation chapters, between-invocation briefs, continuation and fork points, tool calls and results retain the existing transcript rendering. A chapter link from a gate, decision or map marker opens the window at that chapter. The existing full-page transcript route remains the shareable link to a session and point. The map's URL names the focused map element and foreground session; browser-local workspace state may restore open window IDs, sizes and positions on reload. It does not store transcript contents.

Use one update coordinator for the open windows of a run. Initial history is paged per opened session. Subsequent polls pass the open sessions' cursors together through the existing update endpoint, in batches within its 50-session bound. A `more` page is fetched promptly. Minimized windows may keep their state/header current while deferring body retrieval until restored. The map must never start an independent transcript poll for each session marker.

Dragging and resizing have keyboard controls and visible focus. Windows stay within the viewport and can be reset to a usable position. On narrow or touch screens, the same open sessions appear as full-screen panels with a switcher; the transcript behavior is unchanged. Visual window order is independent of session chronology.

## 5. Projection and data ownership

The harness owns the public execution-map projection because it owns the durable run records and their meanings. The web client owns positions, collapse, focus, window state and rendering. It uses the existing `CapabilityProgress`, work item, session, gate and transcript contracts for their full details instead of reinterpreting result prose, commit messages or changed paths.

The proposed `execution-map/1` answer is a normalized index at one run version:

- entry roots and canonical IDs for capabilities, scenarios, work items, iterations, placement requests, requirements, contracts, sessions and gates;
- typed links such as `entry-scenario`, `requires`, `started-for`, `follows`, `requested-by`, `established-by`, `provider-for`, `verification-of`, `proposed-by`, `repair-of` and `session-reaches`, each with its source record or event sequence;
- brief presentation facts needed before drill-down: current states, scenario names and latest non-dry-run results with gate IDs, each cross-module requirement's current revision, contract mode, contract-engineer start, provider work-item state, conformance and verification evidence, full declared-name paths for capability owner or proposed module and work-item module, exceptional iteration scope paths, ordered iteration IDs, gate attempt verdicts and audit status, session role/state/reach, and event moments;
- the current module hierarchy and typed element-to-module relationships, with role (`owner`, `work item`, `consumer`, `provider`, or authorized scope), enough to derive direct participation and reverse highlights without treating planned scope as an actual change; plus per-module captured-writer `+LOC / −LOC`, source invocation IDs, unmapped/binary counts and coverage;
- coverage: returned and total counts, unresolved links, unavailable records and the run version used.

The index should preserve actual many-to-many relationships; the web chooses one display parent only for layout. It should identify one capability across answers by the current exact-slug policy and preserve registry revision references where available. A newer revision or reopened evidence updates the current card while retaining earlier attempts and decisions in its history. No state is written back by the visualization.

The UI marks an unresolved link as unavailable, rather than guessing its source iteration or displaying an empty branch.

## 6. Reading progress and history

Capability state uses the protocol's `todo`, `working`, `completed`, with green reserved for `completed`. `completed` means verified in this run. A provider wait after work starts remains `working`; an exhausted or failed iteration appears as an issue on the work item and gate history, not as a new capability state. Forecast capabilities remain visually separate from required work. Counts of remaining work use recorded entries, work items, scenarios and open requirements; there is no inferred ETA or fixed count of future iterations.

The run header answers **what is happening now** from the current invocation, waits and any published running gate activity. The selected path answers **what happened** from ordered event moments, sessions, revisions and gate attempts. Gates and audits answer **how verification went**. The transcript windows show the underlying agent conversation. Every significant mark links to its record or transcript chapter, so a reader can inspect the evidence behind the visual summary.

## 7. Delivery and acceptance

1. **Execution index and causal links.** Define and publish `execution-map/1` at one run version, including run gate enumeration and exact provider/repair links. Confirm it reconstructs from durable records after server restart and reports partial coverage.
2. **Compound map and companion modules map.** Render entry roots with every associated scenario name and result, canonical capability/work item cards with visible full module paths, local architect lanes, ordered iteration sequences, scope exceptions, colored cross-module requirement branches, provider branches, return links, session markers and every gate attempt. Add the smaller current-modules tree with violet direct-participation marks, captured-writer `+LOC / −LOC` with coverage, and click-driven highlights in both directions. Give **each map independent pan, zoom and fit controls**, plus complete capability and frozen scenario detail panels, focus, collapse, stable links and event selection.
3. **Transcript workspace.** Extract the existing transcript rendering into reusable content, then add the window manager and shared live update coordinator. Preserve full-page routes and transcript semantics.
4. **Scale and accessibility.** Verify large graphs, shared providers, cycles, many sessions, keyboard operation, narrow screens and reconnect behavior against bounded responses.

Acceptance cases should include the real `status-badge-tone` pi run for existing records, plus a scripted nested-provider fixture with two entry roots sharing a provider in another module, a placement request, contract engineer, fake-backed consumer gate, provider conformance, consumer verification, a failed gate followed by repair, a reopened requirement and a cycle notice. The scenario fixture should cover a pending scenario, a dry-run pass, a real pass, a later failure, a withdrawal after a pass, and an integration scenario: green appears only for the last real pass of a still-implemented scenario, every entry scenario is named, and selecting a name displays the entire frozen Gherkin block. Capability cases should show both top-level and lower-level cards turning green when their published state becomes `completed`, an entry staying `working` despite green scenarios while provider verification is open, and green clearing when evidence is reopened. Selecting an entry capability must display its complete analysis description. A browser case should open local architect and engineer transcripts together, move and resize them, receive new entries in one while scrolled back in the other, then close and reopen one. It should verify that a work item's full module path stays visible, that cross-module iteration scope names full paths, and that detached session windows retain the full module path. Separate checks should prove that every session and gate in the run is reachable from the shelf or run band even when its tree branch is collapsed.

Cross-module color cases should include a requested agreement before its contract engineer starts (gray), contract work started with provider implementation still `todo` (blue, with that provider sub-label), provider conformed but consumer verification open (blue), the current consumer requirement verified (green), and a reopened revision returning to its current non-green state. Two consumers of one provider must color independently. An `access-only` agreement becomes green at registration without inventing provider work, and an unavailable provider binding never appears gray by default.

The modules-map browser case should pan and zoom **each map independently**, click an execution node and see its directly related module highlighted, then click a module and see its directly related execution nodes and hidden-match count. It should cover a work item, local architect session, consumer/provider contract, run-wide element with no module, proposed and unplaced modules, and partial coverage. The involvement mark must not appear for initial association, a request or an authorized scope alone. No hover action is required. A line-volume case should group two settled writer invocations across two owned modules, keep an unmapped path and binary path separate, and show a known subtotal as partial when one line record has a gap. A live writer does not yet add to the total. The displayed label and detail must distinguish captured writer changes from net accepted Git change and state the snapshot-method limitation even when record capture is complete.

This is a design proposal, not executable acceptance evidence. The exact wire schema and browser fixture belong in an implementation plan after review of these choices.
