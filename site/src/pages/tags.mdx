# Tags

The tree rules decide [**visibility**](/glossary#module-visible-symbol):
which symbols the chains of exposures bring to each module. Two real needs
are not expressible with visibility alone. Tests need deliberately selected
internals of a module - fakes, in-memory stores, reset hooks - that
production code must never be able to import. Code that runs in a browser
must only import symbols whose entire runtime closure is browser-safe. Both
are the same shape: a fact about the **importing module** and a fact about
the **exposed symbol** have to be compatible, on top of everything the tree
already decided.

**Tags** carry those facts, and they are purely restrictive: a tag can only
*withhold* a symbol that is visible, never expose one. ramify ships two tags;
each gets its own small example universe below, and both universes keep the
tree trivial - two hops deep, everything exposed to the root and back to
every descendant, so visibility is identical in every box by construction.
The tag is the only variable in each picture.

## `testing` - exposing internals to tests only

In this small app, we keep order handling in an `orders` module. Its tests
need an internal that must never become a production dependency: the
`resetOrderStore` hook that clears the module's store between runs. Without
tags we would face a false choice - expose the hook to everyone or to no one.
`testing` resolves it: we expose exactly the internals tests may touch,
tagged, through the ordinary channels.

So `orders` exposes two symbols to its parent - `OrderService`, the real
contract, and `resetOrderStore`, tagged - and `app` exposes both to its
descendants, where `integration-tests` is a testing module beside the
production consumer `billing`. Identical chains, identical arrivals - and one
symbol wears a tag.

Every symbol has a [**tag set**](/glossary#symbol-tagging), assigned once by
its owner and immutable from then on: no module along the way can add, remove
or change a tag, which is why `resetOrderStore`'s chip rides on the owner's
row and on every arrival alike. [A module can carry tags
too](/glossary#module-tagging), declared in its own definition -
`integration-tests` wears its tag as the dashed box filling the node.

And a tag is not just a name: **when a tag is defined, it is
[associated with its availability rule](/glossary#tag-associated-availability-rule),
and it always carries it.** That is why the diagrams always write a tag
behind the glyph of its rule - <TagRef rule="⇥" name="testing" /> - the name
and the rule are one thing. On a symbol, `testing` carries the
**required module tag** rule, written <TagRef rule="⇥" />: the demand rides
out with the symbol and is checked where it lands - the symbol is
[**available**](/glossary#module-available-symbol) from exposure only in
modules carrying the same tag.

Read `billing`'s box: `resetOrderStore` is listed, provenance and all, with
its name struck - **visible there, not available**: you can see it, you
cannot have it. The same strike appears in `app`'s own box: `app` carries no
tag either, and re-exposing a symbol earns no right to import it. In the
testing module the name is plain. Selecting a tagged symbol shows the same
verdicts in motion: exactly the arrivals where it is available blink, and
withheld rows stay dark.

**On a module,** `testing` classifies the files as tests, and everything such
a module owns and exposes is implicitly tagged `testing` - test infrastructure can
never leak into a production contract. And on a symbol the tag is
*exclusive*: a symbol is real contract or test support, never ambiguously
both.

Two properties make this small mechanism enough. There is no global test
channel: `resetOrderStore` reaches the testing module because the chain of
exposures brought it there, not because the importer is a test. And exposing
to descendants is safe at any subtree width: `app` exposes everything it
receives to its descendants without risk, because the availability rule
travels with the symbol and withholds it from untagged modules everywhere the
exposure reaches.

## `browser` - keeping Node code out of the browser

Our second app has a `ui` module that runs in the browser, a `server` module
beside it, and a `shared` module both of them draw on. Browser code must not
pull in Node-only dependencies - and that line runs *through* `shared`, not
between modules: `shared` owns both `formatMoney` (browser-safe) and
`queryDb` (Node-only). Splitting every such module in two would multiply
modules to encode one fact; `browser` states the fact per symbol instead.

The universe is the mirror image of the last one: here the **module** wears
the working tag, and the rule asks the symbols for a match.

**On a module,** `browser` classifies files that run in a browser and carries
the **required symbol tag** rule, written <TagRef rule="⇤" /> - the mirror of
`testing`'s: the demand faces in at the module's door, checked on everything
arriving, and the module may import from exposure only symbols tagged
`browser`. **On a symbol,** `browser` is a falsifiable promise that the
symbol's entire transitive runtime closure is browser-safe, the owner's
private files included. It carries no rule of its own; it is what the
module-side rule asks for. The promise is verified separately, and a false
claim is reported at the owner - never at the importer, which did nothing
wrong by believing it.

Read `ui`'s box: it is a browser module - the same dashed box as the testing
module, labeled <TagRef rule="⇤" name="browser" /> - and `queryDb`'s row in
it is struck: visible there, not available, like `billing`'s struck row in
the last picture. Selecting `queryDb` shows the dynamic version -
`server` lights up and `ui` stays dark.

## The general shape

Two [availability rules](/glossary#tag-based-availability-rules) exist, and
the examples showed one of each: the required module tag
(<TagRef rule="⇥" />, `testing`'s) rides out with the symbol, the required
symbol tag (<TagRef rule="⇤" />, `browser`'s) faces in at the module's door.
When several rules apply to the same symbol and module, all of them must be
satisfied. And **tags never expose**: no rule makes an import possible that
the exposure chain did not already allow. A tag can only *withhold* a symbol
that is visible.

## Type imports

Everything above is about value imports - the ordinary import, the one that
puts another module's code in your bundle. TypeScript's other form,
`import type`, is erased at compile time and carries no runtime dependency,
and it gets one refinement of its own: a symbol is
[**type-available**](/glossary#type-availability) in a module when the
module's files may import it as a type.

The two verdicts can only differ one way - **available always implies
type-available**, never the reverse (the specification decides "no rule is
type-only"). So the full chain is:

> available ⊆ type-available ⊆ visible

Whether a rule exempts type imports follows from what its claim is about:

- **`browser`'s claim is about runtime** - "this closure is safe to
  *execute* in a browser." An erased import executes nothing, so the rule
  covers value imports only. `queryDb` is therefore struck in `ui` (not
  available) yet still type-available there - the unstruck `∗` after its
  struck name is this fact: `ui` may reference its signature -
  `runQuery: typeof queryDb` - without ever bundling the implementation.
- **`testing`'s claim is about coupling** - "this is not part of the
  production contract." A production function typed in terms of a test
  fake violates that at the type level just as thoroughly as at runtime, so
  the rule covers both forms: `resetOrderStore` in `billing` is not even
  type-available.

The diagrams give all of this exactly one character: the strike means "not
available", and an unstruck `∗` after a struck name marks the middle band of
the chain - type-available but not available. Everything else about type
imports lives here in prose, where it can be explained rather than drawn.

## Where the precision lives

The examples on this page are teaching material. The normative document is the
cross-module importability rules specification, which ships with the
repository at `docs/model/cross-module-importability-rules.md` - the tag rules
are its "Contextual rules" section - with the vocabulary defined in the
[glossary](/glossary). Where a page and the specification appear to disagree,
the specification is right.
